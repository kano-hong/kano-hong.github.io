## 問題

這是一個德州撲克平台，2026 年初要在同一條 WebSocket 連線裡加入多款子遊戲：輪盤、百人德州、炸金花、牛牛。當時有三個問題要一起解決：

- **斷線重連的流程很亂。** 重連失敗後玩家會卡住；App 從背景切回來會重複重連；重連回來後，畫面和資料有時對不起來。
- **子遊戲要共用流程。** 登入、大廳、斷線重連這些流程不能每款遊戲各寫一次，但平台也不能因此認識每一款遊戲。
- **壓測要跑真實的流程。** k6 壓測腳本如果自己再寫一套流程，就會和遊戲越差越遠，壓到的不是玩家真正會走的路。

## 我的角色

我設計狀態機的分層和子遊戲註冊表，寫了開發指南，並親手做出第一款輪盤當範本。另一位同事照著指南做出百人德州、炸金花、牛牛 3 款子遊戲；我也負責這個平台的前端分工。

## 決策 1：一個場景一台狀態機

頂層狀態機只管「現在在哪個場景」：載入、登入、大廳、遊戲。每個場景進入時啟動自己的子狀態機（xstate 的 `invoke`），收到的事件一律轉給目前的子狀態機（`forwardTo`）。

這樣每台狀態機都很小，可以單獨測試；網址加上 `?inspect` 還能打開 Stately 的即時狀態圖，除錯時直接看得到現在卡在哪個狀態。

## 決策 2：狀態機只寫「下一步是什麼」

每台狀態機拆成兩個檔案：`LobbyMachine.ts` 只定義狀態和轉換，`LobbyMachine.impl.ts` 才提供實際要做的事，例如送出進桌請求。

```ts
// 遊戲裡（LobbyMachine.impl.ts）：真的送出進桌請求
sendEnterTableRequest: fromPromise(async ({ input }) =>
  GameHandler.sendEnterTableRequest(input.tableId),
),

// k6 壓測裡（LobbyMachine.k6.impl.ts）：同一個名字，換成不依賴 Cocos 的實作
sendEnterTableRequest: fromPromise(async ({ input }) => {
  await new Promise((r) => setTimeout(r, 50)); // 模擬網路延遲
  console.log(`[K6 Mock] Sending enter table request for table: ${input.tableId}`);
}),
```

因為定義裡沒有任何 Cocos 的程式碼，同一份狀態機可以跑在三個地方：遊戲裡、Vitest 單元測試裡、k6 壓測裡。壓測機器人走的就是玩家走的流程，不用另外維護一套。

## 決策 3：斷線重連只有三個事件

所有狀態機都只認三個重連事件：

- `app.reconnecting`：斷線了，進入等待重連的狀態。
- `app.reconnected`：重連完成，附上要回到的場景（大廳或牌桌）。
- `app.backToLogin`：重新登入失敗，回登入頁。

重連的流程集中在 WebSocket 層：先重新登入；斷線前如果在牌桌上，就用記下的上一桌（遊戲 ID 和房間 ID）重新進桌，成功就回到牌桌，進不去就回大廳。各個場景不用自己處理斷線，只要接住這三個事件。

## 決策 4：平台不認識任何一款子遊戲

每款子遊戲只要提供四樣東西，向註冊表登記：

```ts
gameRegistry.register({
  gameId: GameId.Texas100,
  machine: texas100Machine,                          // 這款遊戲的狀態機
  handlerFactory: (model) => new Texas100MessageHandler(model),  // 封包處理
  modelFactory: () => new Texas100GameDataModel({}),  // 資料模型
});
```

WebSocket 層監聽註冊表（MobX `reaction`），一有新遊戲登記就幫它建好訊息處理器和資料模型，封包依 `gameId` 分流。依賴只有一個方向：子遊戲可以用平台的東西，平台永遠不 import 任何一款子遊戲。

開發指南直接寫在型別定義檔的開頭，新增一款遊戲分成 7 個步驟。同事就是照著這份指南，做出了百人德州、炸金花和牛牛。

## 結果

- **第一款輪盤從零到 UAT 約 3 週**，包含轉盤、下注區、籌碼、歷史紀錄、續押和倒數；之後複製出另外 2 款輪盤，3 款一起在 UAT 修了 13 張單。
- **平台在 2026-02 上線正式環境。**
- **同事照框架獨立做出 3 款子遊戲**，平台本身不用改。
- **132 個單元測試**涵蓋各台狀態機與子遊戲；k6 整合測試打通了百人德州從登入到下注的完整流程。

## 學到的事

- **框架好不好用，要看別人能不能照著做。** 我自己做輪盤只能證明框架能用；同事照著指南做出 3 款遊戲，才證明它好用。
- **把副作用推到最外層。** 狀態機只決定「下一步是什麼」，所以同一份定義可以跑在遊戲、單元測試和壓測裡。
- **斷線重連只做一次。** 流程集中在一處、對外只發三個事件，每個場景就不必各寫一套。
